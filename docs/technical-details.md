# Flakebox - Technical Introduction

Note: Due to immaturity this project is part-vision/TODO and part-documentation
at this point.

Flakebox is published a Nix Flake in https://github.com/rustshop/flakebox
repository. This way it can be easily included in any other Flake
of any Rust project.

By the virtue of being a Nix Flake, project using Flakebox can easily
lock its version, update it, override its own inputs, etc. in addition
to the reproducibility that Nix provides.

### The goal

Functionality of Flakebox is meant to offer a complete and consistent
handling of all the common aspects of Rust project development:

* building Rust projects with Rust,
* setting up configuration files (e.g. Git hooks, commit templates, `justfile`),
* integrating all the best lints (e.g. [`typos`](https://github.com/crate-ci/typos), [`semgrep`](https://semgrep.dev/), formatters, etc.),
* integrating all the best utilities,
* setting up GitHub Actions workflow files,
* providing standardized tools and scripts for handling Rust project.

with a possibility to customize and disable each part.

To make it clear: Flakebox doesn't just setup/install some tools. It fully integrates
them into cohesive and convenient environment, so e.g. all relevant lints from
all the enabled linters run both in Git's `pre-commit` hook, and in the CI, etc.
The goal is to get by default a level of end to end polish that only the largest
and most mature projects usually have, all in just few lines of Nix code.

### Pre-commit timing diagnostics

The generated pre-commit hook runs every enabled check with GNU Parallel. Each
worker uses a monotonic clock around the check itself, so time spent waiting for
a worker slot is excluded. A check that takes strictly longer than one second
emits a diagnostic such as:

```text
flakebox: warning: check_semgrep took 1.235s (>1s)
```

The fixed three-digit fraction reports the duration at millisecond precision.
The strict threshold still uses the underlying monotonic measurement, and a
barely-over-threshold result is displayed as `1.001s` rather than a misleading
`1.000s`. Timing is diagnostic only: checks still run with the same
concurrency, output, exit status, and signal behavior.

The generated hook keeps consecutive warnings compact and adds a separator only
when check output lacks a final newline. The internal timer helper's standalone
mode cannot inspect arbitrary inherited standard error portably, so it
conservatively starts its warning with a newline instead.

### Skipping generated commit hooks

Set `FLAKEBOX_SKIP_GIT_HOOKS=1` to bypass Flakebox's generated `pre-commit`
and `commit-msg` checks for one command or environment:

```console
FLAKEBOX_SKIP_GIT_HOOKS=1 git commit
```

Only the exact value `1` enables the bypass; an unset variable or any other
value runs the checks normally. This does not affect hooks not generated by
Flakebox. Git's `git commit --no-verify` is also available as a one-shot
alternative.


### Installing generated commit hooks

Dev-shell entry inspects the enabled hook symlinks and Git's
`commit.template`, but does not change `.git`. When any enabled integration is
missing or outdated, it prints one notice for that shell entry:

```text
ℹ️  Flakebox Git integration is missing or outdated. Run 'flakebox install-hooks'.
```

The notice remains advisory; configured CI checks still enforce repository
policy when local hooks are absent.

Install or refresh the integration explicitly:

```console
flakebox install-hooks
```

The immutable Flakebox candidate controls which integrations are enabled.
Installation records that state in the invoking worktree's Git directory, so a
stale generated file cannot re-enable its hook. The installer compares each
marker, symlink target, dispatcher, and byte-exact effective template setting
first, so an already-correct installation does not rewrite them. Concurrent
installer processes serialize on `flakebox-install-hooks.lock` in the Git common
directory. Hook, dispatcher, and marker updates create a neighboring entry and
rename it into place, so readers see either the previous entry or the complete
new entry. Git updates the configuration through its own `config.lock`
transaction.

All hook ownership, filesystem inspection, template ownership, dormant
worktree-config inspection, and worktree-configuration safeguards produce one
validated plan under the installer lock before the first hook, marker,
dispatcher, or Git-config mutation. A foreign worktree template or hook therefore
makes the command fail without changing either subsystem. Dispatchers and markers
must be regular files. Markers require exact Flakebox content and mode;
dispatchers require that match or the installed reserved hook link as separate
ownership evidence. Symlinks do not prove file ownership even when their targets
provide the same bytes. Reserved parent namespaces must also be real directories;
Flakebox refuses symlinked parents instead of following them.

Linked worktrees share their Git hook directory. Each installed hook therefore
points to a shared Flakebox dispatcher, which asks Git for the invoking worktree
and runs that worktree's generated policy when present. A disabled worktree
therefore no-ops without removing a dispatcher another worktree needs.
`commit.template` uses Git's worktree-specific configuration so enablement can
differ independently. Installing an enabled template verifies and locally
enables `extensions.worktreeConfig`, then migrates an exact legacy Flakebox
template value out of shared local configuration. A wholly disabled or
hook-only installation does not enable the extension. Flakebox refuses
activation when non-default local `core.worktree` or `core.bare` values require
manual migration under Git's worktree-config rules.

The Flakebox lock coordinates only `flakebox install-hooks` processes. Apply
creates temporary entries exclusively, preserves unexpected temporary occupants,
and revalidates each destination immediately before destructive replacement.
An unrelated process can still win the narrow interval between revalidation and
rename, change an installed entry afterward, or race for `.git/config.lock`.
Configuration apply similarly maintains rolling file snapshots, revalidates
immediately before every Git command, and restricts removals to the exact
Flakebox value. The residual race is one check-and-command interval rather than
the whole multi-command apply phase.
Flakebox therefore guarantees mutation-free validation refusals and avoids
knowingly overwriting concurrent foreign state, but it does not claim a
multi-file transaction against writers that ignore its lock. The persistent
lock file avoids stale-lock recovery because the operating system releases its
advisory lock when a process exits.

A failed write or rename can preserve the named PID-scoped temporary path. This
is deliberate: an outside writer may have replaced that path, so automatic
cleanup could delete foreign state. Inspect and remove the path named in the
error before retrying. Reruns converge managed destinations, not unknown
temporary occupants.


### Disabling commit integration

Set `git.enable = false` in the Flakebox configuration to disable the complete
Git commit integration. Flakebox then does not generate or install its
`pre-commit` or `commit-msg` hooks, generate its commit-message template, or
prompt for Git's `commit.template` configuration. The existing
`git.pre-commit.enable`, `git.commit-msg.enable`, and
`git.commit-template.enable` options remain available for partial control when
`git.enable` is true.

This option does not remove shared hook links or dispatchers because another
linked worktree may still need them. The shared dispatcher no-ops in a worktree
whose generated hook is absent. Running `flakebox install-hooks` after disabling
the template removes only this worktree's exact Flakebox-owned template setting;
foreign worktree and shared local values remain unchanged. Remove old generated
worktree files separately:

The installer removes a legacy direct hook link only when it points to the
invoking worktree's exact generated hook. It preserves and reports an ambiguous
legacy-style target elsewhere because that target may belong to another
worktree or tool. Enabled installation likewise refuses to replace a regular
hook or foreign symlink; preserve or remove that entry explicitly first.

```console
rm -f misc/git-hooks/pre-commit \
  misc/git-hooks/commit-msg \
  misc/git-hooks/commit-template.txt
```

Shared-hook removal is a repository-wide operation. First list every worktree
and verify that each has disabled both integrations:

```console
git worktree list
```

Only then confirm that the common hooks are Flakebox-owned and remove the
top-level links and dispatchers together:

```console
hooks_dir="$(git rev-parse --git-common-dir)/hooks"
ls -l "$hooks_dir/pre-commit" "$hooks_dir/commit-msg"
rm -f "$hooks_dir/pre-commit" \
  "$hooks_dir/commit-msg" \
  "$hooks_dir/flakebox/pre-commit" \
  "$hooks_dir/flakebox/commit-msg"
```

Use the installer for byte-exact cleanup of this worktree's owned template
setting:

```console
flakebox install-hooks
```

## Flakebox `lib` output

Flakebox's Flake exposes a `lib` flake output which allows:

* creating Flakebox Nix development shells,
* customizing all settings,
* extending with own modules,
* building project artifacts form Rust code using Nix derivations.

## Flakebox Nix development shells

Flakebox Nix development shells are standard `nix develop` shells,
but with all the integration and configuration taken care of.

To facilitate generation of tool/service/application specific
files, and for other DX purposes a `flakebox` CLI tool is prided
in development shells.

`Flakebox` will detect when its flake input, or desired configuration
changed and prompt the user to run `flakebox install` to update
all the generated files, which can then be committed into the project.
This is done so that all the tools (like GitHub Actions) expecting files
in certain places, and all the users viewing the project without
using development shells find everything where they expect.


### Updating Flakebox

To update the Flakebox version used by the project, one would start by updating
its flake input, e.g. with `nix flake update`.

Then the Nix development shell will prompt the user to run `flakebox install`,
which will then overwrite old files with their new versions. All changes
can be then committed and pushed a PR to the project.
